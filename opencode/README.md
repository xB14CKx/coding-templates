# OpenCode Template — WARROOM

A portable OpenCode setup for any project architecture. Orchestrated agents, a
durable second brain, config-enforced safety rails, and a protocol for running
work in parallel.

Stack-agnostic on purpose. Everything specific to your project lives in
`CONVENTIONS.md` and `.opencode/brain/` — not in the agents.

---

## Install

```sh
cp -r /path/to/this/template/.opencode /path/to/your/project/
cp /path/to/this/template/AGENTS.md      /path/to/your/project/
cp /path/to/this/template/CONVENTIONS.md /path/to/your/project/
```

> **`opencode/.opencode` is not a duplicate. It is the copy unit.** The outer
> folder is only a label inside this templates repo. OpenCode reads project
> config, agents, skills and commands from a directory with the *exact* name
> `.opencode/`, so it can be neither renamed nor flattened — and the same
> pattern holds for `antigravity-cli-setup/.agents` and `kiro-cli-setup/.kiro`.
> Copying `.opencode/` into a project gives that project its config; the outer
> folder itself is never copied.

Both paths matter. `AGENTS.md` must sit at the **project root** — OpenCode only
loads instruction files from there, and `.opencode/AGENTS.md` is never read.

Then open the project and run:

```text
/onboard
```

That detects your stack, writes `.opencode/brain/stack.md`, and fills in
`CONVENTIONS.md`. Commit the result — the brain and the conventions are
project-owned and belong in version control.

## The structure

```
AGENTS.md                        always-loaded contract: priority, rules, routing
CONVENTIONS.md                   this project's real rules and commands
README.md                        this file
PLUGINS.md                       curated plugin shortlist, and what to avoid
.opencode/
├── opencode.jsonc               default agent, hard denies, prompt rules
├── scripts/verify-template.js   structural check: agents, skills, commands
├── scripts/policy-check.js      regression test for the deny table
├── scripts/set-descriptions.js  rewrites the @-picker blurbs in agents/*.md
├── agents/                      the ten units
├── skills/                      protocol, loaded on demand
│   └── onboarding/reference/profiles/   per-architecture playbooks
├── commands/                    /onboard /plan /parallel /ship /review …
├── plans/                       cartographer's plan files, created on demand
└── brain/                       the project's durable memory
    ├── INDEX.md                 grep this
    ├── stack.md                 detected stack and verified commands
    ├── decisions/  patterns/  pitfalls/  inbox.md
```

`package.json`, `package-lock.json`, and `node_modules/` are generated by
OpenCode, not authored here — they hold only the plugin SDK and are gitignored.

## The units

`WARROOM` is the default agent. It classifies, briefs, dispatches, verifies, and
reports. You never have to pick a unit — but you always can.

| Unit | Owns | Mode |
|---|---|---|
| `warroom` | orchestration, delegation, verification, integration | read/write |
| `outrider` | fast search, grep, file discovery | read-only |
| `cipher` | external docs, web search, prior art | read-only |
| `cartographer` | planning, architecture, design decisions | plan files only |
| `hammer` | precise code changes | read/write |
| `mason` | UI/UX, frontend, styling, accessibility | read/write |
| `examiner` | deep reasoning, root-cause, hard bugs | read-only |
| `aegis` | threat and trust-boundary review | read-only |
| `adjutant` | docs, comments, ADRs, changelogs | read/write |
| `quartermaster` | git analysis, commit and PR text | read-only |

Eight named callsigns plus two real military roles — the adjutant kept the
records, the quartermaster kept the manifest. Every unit is `mode: all`, so
`@hammer`, `@aegis`, and the rest can be selected directly from the composer
when you want to bypass the chain.

### Callsign cheat sheet

Type `@` in the composer and each unit shows its purpose — you do not need to
remember these:

| @ | One-line job |
|---|---|
| `@warroom` | orchestrates, delegates, verifies — the default |
| `@outrider` | finds things: files, symbols, callers |
| `@cipher` | looks things up: docs, APIs, versions |
| `@cartographer` | plans the route: options and trade-offs |
| `@hammer` | makes the change: code, decided plan |
| `@mason` | builds the interface: UI, styling, a11y |
| `@examiner` | finds the cause: hard bugs, races |
| `@aegis` | guards the boundary: security review |
| `@adjutant` | keeps the record: docs, ADRs, brain |
| `@quartermaster` | reads git: state, commit and PR text |

> An agent's display `name` is derived from its filename and **cannot be set from
> frontmatter** — verified against a running server. The `description` is
> therefore the only text the `@` picker has, so each one leads with the callsign
> and the job before the routing detail. Change them with
> `node .opencode/scripts/set-descriptions.js`.

## Before it actually works

The structure is finished and verified. Two things are left for you, because
guessing them produces a setup that looks configured and is not. The third is a
check only you can run.

**1 — Run `/onboard` in a real project.** Until you do, `brain/stack.md` and
`CONVENTIONS.md` are templates, and six of the ten unit prompts tell the agent to
read a file that contains placeholders. This is the single biggest gap.

**2 — Retarget the models (Block 3) if you are not on this account.** The block
ships populated, with every unit on a zero-priced model from the `opencode`
provider. On any other provider it is the one thing you must edit. See Speed
below.

**3 — Confirm the deny table actually blocks.** `policy-check.js` proves the
patterns match what they claim. It cannot prove the running server enforces
them — only a real denied tool call can, which needs a funded provider.

## Plugins

You don't need any. The template is self-contained — ten units, ten commands,
nine skills, the brain, and the safety rails all ship in `.opencode/`.

[`PLUGINS.md`](./PLUGINS.md) is a short "what not to install" list, because the
ecosystem has seven full orchestrators that each ship their own agents. Picking
one of those instead of this template is a reasonable choice. Picking one *and*
this one leaves you with two orchestrators and no reliable routing.

## Commands

| Command | What it does |
|---|---|
| `/onboard` | Detect the stack, write the brain and conventions |
| `/plan` | Smallest complete diff, before any edit |
| `/parallel` | Explicit fan-out with a stated partition rule |
| `/ship` | Full pipeline: understand → recon → decide → implement → review → verify → record |
| `/review` | Review the diff for defects, risks, scope creep |
| `/verify` | Run the checks, report honestly what passed |
| `/security` | Full security audit (runs as a background unit) |
| `/commit` | Commit message and PR text (runs as a background unit) |
| `/recall` | What the brain already knows about a topic |
| `/record` | Record a decision, pattern, or pitfall |

## Safety rails

`opencode.jsonc` holds three labelled blocks.

**Block 1 — hard denies (`policies`).** Evaluated *after* agent permissions and
*after* saved "Allow always" approvals, so no prompt and no project config can
re-enable them:

- All git is denied, then the read-only inspection set is re-allowed. The
  developer owns git state; the agents read it and write the commit text.
- `gh`, `hub`, `glab` — no PR or release is ever created from here.
- `sudo`, `su`, `doas`, and the blunt destructive commands.
- Reads and writes of real secret material: `.env`, `Secrets/`, `.ssh`, `.aws`,
  `.npmrc`, private keys. `.env.example` stays readable.
- Narrow re-denies so read-only git inspection cannot be used to pull a
  committed secret back out of history.

**Block 2 — prompt-worthy operations (`permissions`).** The base policy allows
everything, which is what makes this fast. Consequential commands are listed
here so they ask first: network fetch, dependency installation, destructive
deletes, and hand-edits to lockfiles. Tune freely — delete a line to remove the
prompt, add one to add a prompt.

**Block 3 — agent scope (`agents`).** Cross-cutting overrides only. Per-agent
permissions live beside each agent in `agents/*.md` so a unit travels with its
own file. All units now inherit the session's selected model (the top-level
`model`); there is no per-agent model tiering.

> **Want the agent to manage git?** Delete the whole git group from Block 1. That
> is the single deliberate concession this template makes, and it is one
> deletion.

**After editing Block 1, run the regression test:**

```sh
node .opencode/scripts/policy-check.js   # 107 deny/allow assertions
node .opencode/scripts/verify-template.js  # agents, skills, commands, config
```

`policy-check` reimplements OpenCode's documented matcher and asserts the
verdict for every git mutator, every secret path, and the
privilege-escalation set. The git rules are subtle enough to break silently: a
trailing `*` also matches the bare command, which is how a bare `git stash` (a
push, not a list) almost slipped through. Extend the table when you add a
policy.

`verify-template` catches mechanical breakage — a rename that missed a
reference, a command pointing at an agent that no longer exists, a missing
frontmatter field.

**Two known limits, documented rather than hidden:**

- `rm -rf /*` cannot be hard-denied — matching an argument that is literally
  `/*` needs an escaped `*`, which the policy language does not have. It falls
  through to the `rm -rf *` ask rule instead. Hard-denying all absolute paths
  would have made the policy unusable.
- These live under `experimental.policies` because v2.0.27 silently drops a
  top-level `policies` key. Once a build accepts it, move the array up one level
  with no other change.
- A global flag before the subcommand (`git -C dir status`) matches no
  `git <cmd>*` pattern and falls into the blanket deny. The common read-only
  forms are covered explicitly; if you add a git pattern, add the `-C` variant
  too, and extend the check table.

## The brain

`.opencode/brain/` is what the project knows that the code does not say. It is
committed, shared, and cheap to grep.

- **Before** working an unfamiliar area, `grep` `INDEX.md` and read only what
  matches.
- **After** a task that revealed something non-obvious, write one short note
  and add one index line.

Four kinds: `decisions/` (why), `patterns/` (how), `pitfalls/` (what broke),
`stack.md` (what this is). Every entry cites a `path:line`, a command output, or
a named incident — an uncited note is a rumour that will be trusted as fact.

Budget: roughly 30 entries. Past that, a brain stops being a lookup table and
becomes an archive nobody reads.

## Parallel work

The `dispatch` skill carries the full protocol. In short:

1. Parallelize only when tracks are genuinely independent and you can name the
   partition in one sentence.
2. Partition writes so **no file appears in two briefs**. Fix the partition
   before dispatching, not after the conflict.
3. Launch the independent tracks together, in the background. They notify you
   when done — do not poll or sleep.
4. Reconcile: `git diff --stat` against what each unit *claimed*. The report is
   the first thing to be wrong.

Every unit returns the same handoff shape — `STATUS / CHANGED / VERIFIED /
OPEN` — which is what makes parallel results reconcilable instead of a pile of
prose. Three to five concurrent units is the practical ceiling. Past that you
lose track of who reported what, and the wide fan-out returns weaker work rather
than faster work.

## Tuning

Where to spend your time when results feel slow or wrong.

### Speed

The setup is permissive by default and relies on policies rather than prompts.

**All units use the session's selected model.** There is no per-agent model
tiering — the single top-level `model` in `opencode.jsonc` is the one line that
moves every routing decision at once. Config `agents` now carries only
cross-cutting scope (such as the `warroom` subagent deny); no `model` key is
set for any unit, so they all inherit the session default.

Check what actually resolved rather than trusting the table:

```sh
opencode debug agents   # prints the model each unit really gets
```

| Unit | Model | Why |
|---|---|---|
| all units | *session default* (`opencode/big-pickle`) | One top-level line moves every routing decision at once |

Two sharp edges that cost real time:

- **`opencode run --agent <name>`** also uses the top-level `model`, so CLI and
  subagent dispatch now agree — no more mismatch between the two paths.
- **Do not add `#high` reflexively.** Measured here, one free model scored 4.33
  plain and 3.67 at `#high` over 3 trials. The higher-effort setting was worse.

`small_model` (Block 0) is legacy on v2.0.27 and reaches only session-title
generation — not summary, not compaction. Left unset it falls back to a cheap
model the provider exposes, or to the session model if it exposes none. It ships
commented out.

**Other knobs:** each unit has a `steps:` cap bounding worst-case cost;
`compaction.keep.tokens` trades exactness against headroom; `warming` is off by
default because every warming request is a real billed call.

**Context.** `AGENTS.md` is deliberately short. Everything else loads on demand.
If it grows past ~100 lines it is doing a skill's job — move the detail out.

**A note on `instructions`.** The V2 config schema accepts an `instructions`
array but does not resolve it yet, so rules put there reach nothing. Use
`AGENTS.md`. This template ships none, and that is intentional rather than an
oversight.

## Adapting for your project

The template stays generic; the project gets specific, in three places:

| File | Holds | Written by |
|---|---|---|
| `CONVENTIONS.md` | your rules, commands, layering | `/onboard`, then humans |
| `.opencode/brain/stack.md` | detected stack, verified commands | `/onboard` |
| `.opencode/brain/*` | decisions, patterns, pitfalls | any unit, per the skill |

To add a **unit**: drop a Markdown file in `.opencode/agents/`, set
`description` so it is distinguishable from the others, pick `mode`, and add the
`subagent` allow rule in `.opencode/agents/warroom.md`. To add an **architecture profile**:
drop a file in `skills/onboarding/reference/profiles/` and add a row to that
skill's table.
